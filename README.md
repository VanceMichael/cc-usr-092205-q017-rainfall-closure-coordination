# 持续降雨联合停课封路

协调持续强降雨下的停课、封路、校车运营与公众行动指引，解决“家长先收到停课通知、几分钟后校车系统却提示正常发车”这类跨部门信息矛盾。

## 领域规则

- **统一格点**：气象、道路、教育等部门共用同一套预报格点（`cells`）。预报落区、实况雨量、地质灾害点、积水道路、学校、校车线路和避险场所都先映射到格点，再做空间判定。
- **真正相交**：预警升级或雨带移动后，只影响与落区几何上真正相交的学校、道路、校车线路；跨区道路自然覆盖多个格点与区县。
- **原始时刻保留**：事件流只追加（`events`）。签发、生效、撤销、撤回、拒绝各有自己的时刻；有效期按 ISO 8601 带时区时刻比较，跨午夜降雨无需特殊处理。
- **分部门负责**：教育部门签发停课/恢复上课（限本区县学校），交通部门签发校车停运/恢复运营，应急部门签发封路/解封，气象部门发布预警。越权签发或撤销会被拒绝。
- **恢复条件写明**：恢复上课、解封、恢复运营前必须逐条核验观测条件——观测窗口累计雨量不超上限、预警等级不高于允许值、没有仍有效的相关人工上报，且窗口内观测完整；**传感器离线期间不得解封/复课**。
- **发布前拦截矛盾**：各部门决定进入同一事件流，对外发布闸门检查“学校已停课但校车仍正常”“道路已封但校车仍发车”等矛盾组合，矛盾时拦截并记录拦截时刻与原因，公众永远不会同时收到互相矛盾的通知。
- **单一版本**：每次对外发布生成带版本号的快照，家长、司机、救援人员看到同一版本，按各自当前位置（所在格点）与角色过滤出当前有效行动，并附上就近避险场所。

人工上报（如道路积水）可能是误报：误报在撤回前按有效处理并阻断恢复，撤回后恢复放行；原上报与撤回时刻都保留。

## 资料约定

`contracts/domain.schema.json` 描述共享资料的字段结构，`fixtures/domain.json` 是不含真实个人信息的业务样例，重放了 2026-07-12 暴雨夜的完整处置过程（`tools/build_fixture.py`，事件均为虚构）：

1. 19:50 橙色预警落区 G1、G2，有效期跨午夜；
2. 20:05 教育部门先对 S1 停课，20:08 对外发布被闸门拦截（校车 B1 尚未停运），拦截留痕；20:15–20:25 校车停运、S3 停课、R2 封路联动完成，第 2 版通告发布；
3. 21:10 应急部门误封与落区不相交的 R3，21:40 复核撤销；21:45 封闭跨区道路 R1；
4. 21:50 预警升级红色并扩大到 G3（取代旧预警），S2 停课；23:20 雨带移至 G3、G4（再次取代）；
5. 次日 01:20 人工上报 R2 积水；02:00 解封申请因雨量超标、红色预警、上报未撤回被拒；02:30 确认误报撤回；02:45 再申请因雨量站 P2 离线被拒；04:50 传感器恢复且条件满足，05:00 R2 解封；
6. 早晨各校按各自观测条件陆续恢复上课；校车在所有服务学校复课、途经道路解封后才恢复运营，最终第 5 版通告中公众只看到当前有效行动。

代码模块：`src/geo.py`（格点与几何相交）、`src/timeline.py`（只追加事件流、跨午夜状态回放、雨量与离线判定）、`src/decisions.py`（分部门签发、恢复条件核验、矛盾检查）、`src/bulletin.py`（发布闸门与按位置/角色的单版本通告）、`src/domain.py`（资料加载与引用完整性校验）。
